# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start the Vite dev server with HMR
- `npm run build` — type-check (`tsc -b`, which also checks the worker through `tsconfig.worker.json`) then production-build via Vite
- `npm run lint` — run oxlint
- `npm run test` — run the Vitest suite once (CI mode)
- `npm run test:watch` — run Vitest in watch mode
- Run a single test file: `npx vitest run src/App.test.tsx`
- Run tests matching a name: `npx vitest run -t "adds a todo"`
- `npm run worker:dev` — run the sync API locally on http://127.0.0.1:8787. Needs `npm run db:migrate:local` once, and a git-ignored `.dev.vars` containing `ACCESS_KEY=dev` and `ALLOWED_ORIGIN=http://localhost:5173,http://127.0.0.1:5173`. `npm run dev` then talks to it (`.env.development`); open `http://localhost:5173/#cle=dev`.
- `npm run worker:deploy` — deploy the sync API to Cloudflare. Run `npm run db:migrate:remote` first when there's a pending migration.

## Architecture

Single-page React 19 + TypeScript app scaffolded with Vite and served by GitHub Pages. Todos persist to `localStorage` (key `todo-app:v1`) and, once the device has the shared access code, sync through a small Cloudflare Worker + D1 API in `worker/` (see **Sync** below). Without a code the app is local-only, exactly as before sync existed. No accounts. Gamification (level/XP/streak) is never stored on the `Todo` itself; it's derived fresh from the todos array (plus the archived-completions array, see below) on every render, so toggling a task back to not-done still automatically retracts the XP/streak it granted. Deleting a *completed* task is the one exception: its `{ completedAt, difficulty }` is banked into a separate archived-completions store first, so XP/streak/chart credit survives even though the task itself is gone for good.

Tasks are split into three **zones** (`hector`, `nina`, `commun`). Every `Todo` and `ArchivedCompletion` carries its `zone`; all zones live in the same two storage arrays and `App` filters them down to the open zone, so everything below the zone picker (task list, header XP/streak, stats page) only ever sees one zone's data — level/XP/streak are per zone. All three zones are synced: every device with the access code sees every zone.

- `src/types.ts` — `Todo` (`id`, `text`, `createdAt`, `dueAt?`, `difficulty`, `done`, `completedAt?`, `parentId?`, `zone`), `Difficulty`, `DIFFICULTY_OPTIONS` (value/label pairs for the difficulty picker UI — lives here rather than in a component so it stays a plain export for fast refresh), `Zone`, `ZONES` (menu order), `ZONE_LABELS`, `ArchivedCompletion` (`id`, `completedAt`, `difficulty`, `zone` — the minimal facts kept for a deleted completed task; `id` exists so the server can deduplicate it), `SyncSnapshot` (`{ todos, archived }` — a device's or the server's whole synced state), `SyncChanges` (`{ upserts, deletes, archived }` — the body of `POST /api/sync`), `GamificationSnapshot`, `Urgency`. Also imported by the worker, so it must stay DOM-free.
- `src/validation.ts` — type guards shared by the app and the worker (so it must stay DOM-free too): loose `isStoredTodo`/`isStoredArchivedCompletion` for local storage (zone and archived `id` may be missing), strict `isTodo`/`isArchivedCompletion` for anything exchanged with the server, and `parseSnapshot` (drops invalid entries) / `parseChanges` (rejects the whole body if any entry is invalid).
- `src/storage.ts` — `loadTodos`/`saveTodos` (key `todo-app:v1`), `loadArchivedCompletions`/`saveArchivedCompletions` (key `todo-app:archived:v1`), `loadSyncBase`/`saveSyncBase` (key `todo-app:base:v1`, see Sync) and `loadAccessKey`/`saveAccessKey` (key `todo-app:key:v1`), all `localStorage` read/write guarded by try/catch (storage-disabled browsers fall back to in-memory for the session) and filtered through the `validation.ts` guards on load so corrupted/foreign entries are dropped rather than crashing gamification math. Entries saved before zones existed have no `zone` field; on load they (and any unknown zone value) are assigned `LEGACY_ZONE` (`hector`). Archived entries saved before sync existed have no `id`; on load they get a fresh UUID, persisted by the next save. Neither needed a storage key bump.
- `src/dateUtils.ts` — pure date helpers: `formatRelativeTimeAgo`, `formatDueLabel`, `getUrgency`, `toLocalDateKey`, `calendarDayDiff`, `addDays`. All accept an explicit `nowMs` for deterministic tests.
- `src/gamification.ts` — `XP_BY_DIFFICULTY`, `levelForXp` (quadratic level curve, `cumulativeXpForLevel(L) = 50*L*(L-1)`), `computeStreak(todos, nowMs, archived)` (consecutive local-calendar-days with a completion, anchored on today-or-yesterday), `xpByDay(todos, days, nowMs, archived)` (XP earned per local day over a trailing window, oldest first — feeds the stats chart), `deriveGamification(todos, nowMs, archived)`. Each takes an optional `archived: ArchivedCompletion[] = []` (appended last, so old call sites still compile) that's folded into the same date-bucket/XP-sum logic as live done todos. Operates over the flat todos array regardless of subtask nesting — a completed subtask grants XP same as any other done todo, and this same per-item independence is preserved when subtasks are archived on deletion (a done parent plus its done subtasks each bank their own entry).
- `src/subtasks.ts` — pure helpers for the two-level subtask model: `getSubtasks(todos, parentId)` (direct children, oldest first), `hasSubtasks`, `canNest(todos, childId, parentId)` (rejects self-nesting, nesting across zones, nesting under a subtask or beneath a completed task, and nesting a task that already has its own subtasks — this caps depth at two levels).
- `src/todoSort.ts` — `groupAndSortTodos` buckets *top-level* todos (`parentId === undefined`) into overdue/dueSoon/upcoming/noDate and separates done todos, each bucket sorted appropriately; subtasks are excluded since they render nested under their parent instead.
- `src/hooks/useTodos.ts` — localStorage-backed CRUD (`addTodo`, `toggleTodo`, `updateTodo`, `deleteTodo`, `nestTodo`), plus `archivedCompletions` state (also localStorage-backed), plus `replaceAll(snapshot)` (a stable `useCallback`) that swaps in a whole synced state — it's how `useSync` applies the server's answer. It holds every zone's todos; `addTodo({ text, difficulty, dueAt?, zone })` stamps the zone, and archived entries copy the deleted todo's zone. `toggleTodo` sets/clears `completedAt` and cascades: toggling a task also toggles all of its subtasks, and toggling a subtask re-derives its parent's `done` via `syncParentDone` (done once every subtask is done, un-done the moment one isn't — symmetric with the XP-retraction philosophy above). `updateTodo(id, { text, difficulty, dueAt })` replaces those three editable fields wholesale (the edit form always submits full current values, so there's no partial-update ambiguity). `deleteTodo` cascades to a parent's subtasks (same as before) and, before removing anything, banks a `{ id, completedAt, difficulty, zone }` entry (fresh UUID) into `archivedCompletions` for every removed item that was done — so deleting a completed task (or a completed parent/subtask caught in the cascade) preserves its XP/streak/chart contribution. `nestTodo` sets `parentId` after checking `canNest`, then re-syncs the new parent's done state.
- `src/hooks/useGamification.ts` — `useMemo` wrapper over `deriveGamification(todos, nowMs, archived)`; takes `(todos, archived = [], nowMs = Date.now())`.
- `src/hooks/useSync.ts` — keeps `useTodos`' state in step with the server; see **Sync**.
- `src/components/TaskFields.tsx` — `DifficultyPicker` and `DueDatePicker`, the two form controls shared between `AddTaskForm` (add mode) and `EditTaskForm` (edit mode) so the two forms can't drift apart.
- `src/components/EditTaskForm.tsx` — in-place edit form rendered by `TaskItem` in place of the row when editing; pre-fills from the todo, submits the full `{ text, difficulty, dueAt }` via `onSave` to `useTodos#updateTodo`.
- `src/components/ZonePicker.tsx` — the entry screen: one button per zone with its count of open top-level tasks. The app always opens on it (the chosen zone isn't persisted).
- `src/components/SyncStatus.tsx` — one quiet status line rendered by `App` under the zone picker ("Synchronisé", "Hors ligne — …", "Sur cet appareil seulement", …). It's also where a device types the access code ("Se connecter" / "Changer de code" → a small form reusing `.add-task-row` styles). The typed code is required on an installed iPhone app, whose storage is separate from Safari's and so never sees a code opened through a `#cle=` link.
- `src/components/ProgressHeader.tsx`, `AddTaskForm.tsx`, `TaskList.tsx`, `TaskItem.tsx`, `StatsPage.tsx` — presentation; `ProgressHeader`'s title is the open zone's name as a `.zone-switch` button (`onChangeZone`) that returns to the zone picker; `AddTaskForm` knows nothing about zones (`App` adds the open zone when it calls `addTodo`); `AddTaskForm` uses progressive disclosure (due date + difficulty are hidden behind an "Add details" toggle). `TaskItem` renders a row split into `.task-toggle` (checkbox + text, sized to content — only this region toggles the task) and `.task-row-actions` (drag handle + discreet `.icon-button` edit/delete icons, pushed right via `margin-left:auto`, dimmed via `opacity` until hover/focus), so tapping empty space on the row does nothing; a top-level task with subtasks renders them recursively (one level only) inside a nested `.subtask-list`, alongside a done-count badge. `TaskList` owns the drag-to-nest gesture: a pointer-events-based drag (not HTML5 DnD, which doesn't fire on touch) on each childless top-level task's `.drag-handle`, using `setPointerCapture` + `document.elementFromPoint` to track the hovered `[data-todo-id]` li and a fixed-position `.drag-ghost` label that follows the pointer; on release it calls `onNest` if the hovered target is valid per `canNest`. `StatsPage` is a second full-screen view (level/XP/streak/done-count tiles, a CSS-bar `xpByDay` chart over the last 14 days fed by both live `todos` and `archivedCompletions`, and a static rules explainer sourced from the live `XP_BY_DIFFICULTY`/`cumulativeXpForLevel` constants so it can't drift from the real numbers) — `App` swaps between it and the task list via local `view` state; `ProgressHeader`'s `📊` button (`onOpenStats`) opens it, `StatsPage`'s back button (labelled with the zone name via `backLabel`) returns. No router: the app is small enough that a single `useState` toggle in `App.tsx` is simpler than adding a routing dependency.
- `.todo-list li button` has no blanket style rule — every direct action button in a task row (`.icon-button`, `.drag-handle`) carries its class explicitly. Don't reintroduce a bare `li button` selector: form controls (difficulty/due-date pickers) render inside the same `<li>` during edit mode, and a high-specificity `li button` rule would clobber their borders/backgrounds.
- `src/App.tsx` — composition root: wires `useTodos` and `useSync` to the components, holds the open `zone` (`null` = zone picker, with `SyncStatus` under it) and the `view` ('tasks' | 'stats') toggle, and memo-filters todos/archived completions to the open zone before handing them to `useGamification` and the components.
- `src/main.tsx` — React root mount point. Before mounting, `adoptAccessKeyFromLocation` (`src/sync/config.ts`) stores an access code passed as `#cle=<code>` and strips it from the address bar. It also does this on `hashchange`, then reloads. Opening the link in a tab that already shows the app changes only the fragment, with no page load, so without this listener the code would be ignored and the device would stay local-only.
- `src/setupTests.ts` — Vitest setup file, loads `@testing-library/jest-dom` matchers and clears `localStorage` after each test; wired in via `test.setupFiles` in `vite.config.ts`.

`vite.config.ts` sets `base: './'` so the production build works when served from any nested path (e.g. GitHub Pages project subfolders).

The UI is in French (matching the rest of the `claudeapps` collection). `public/manifest.webmanifest`, `public/favicon.svg` (doubles as the PWA icon), and `public/sw.js` (a network-first, runtime-caching service worker — no static asset list, since Vite's build output filenames are hashed) are copied verbatim into the build by Vite's `public/` convention and registered from `src/main.tsx`, so the app installs to a phone's home screen and keeps working offline after a first visit, matching the other apps in the repo. `sw.js` only intercepts same-origin GETs, so calls to the sync API (another origin) never go through its cache.

`main.tsx` checks for a new service worker at launch, whenever the app returns to the foreground, and once an hour. When one takes control, it reloads the page once. The check only compares `sw.js` itself, so an app left open on an old build picks up a new release only if `sw.js` changed. For releases that must reach every device, such as the sync release, bump its `CACHE` name.

Testing uses Vitest + `@testing-library/react` + `@testing-library/user-event`, run in a `jsdom` environment (configured in `vite.config.ts`'s `test` block, alongside the Vite/React plugin config — this is a single-config-file setup, not a separate `vitest.config.ts`).

Linting uses oxlint (`.oxlintrc.json`), not ESLint.

## Sync

- **Server** — `worker/index.ts` is a plain `fetch` handler deployed as the Worker `taches-api` (`wrangler.jsonc`), backed by the D1 database `taches` (`migrations/`).
  - Routes: `GET /api/health`; `GET /api/state` → `SyncSnapshot`; `POST /api/sync` with `SyncChanges` → applies them in one D1 batch and answers with the full `SyncSnapshot`. The batch has one `json_each` statement per kind of change, whatever the item count, because D1 caps queries per request.
  - Auth: one shared code in `Authorization: Bearer`, compared (hashed, `timingSafeEqual`) against the `ACCESS_KEY` secret. A wrong code gets `404`, like an unknown route.
  - CORS is granted only to `ALLOWED_ORIGIN` (the Pages origin in `wrangler.jsonc`, overridden by `.dev.vars` locally; comma-separated).
  - Storage: each todo row keeps the whole `Todo` JSON in `data`, so new `Todo` fields need no migration. `zone`, `due_at` and `done` are also copied into real columns for server-side queries (meant for future due-date notifications: a cron-triggered `scheduled` handler plus Web Push from `sw.js`).
  - Deleting writes a tombstone (`deleted = 1`), and an upsert never overwrites a tombstone, so a stale offline edit can't resurrect a task deleted on another device. Archived completions are insert-or-ignore by `id`.
- **Model** — `src/sync/diff.ts`.
  - Each device keeps a **base**: the last `SyncSnapshot` the server confirmed (`todo-app:base:v1`). Pending changes are always `diffState(base, current)`, so there is no outbox: offline edits survive a reload because both snapshots are stored.
  - Todos compare key-order-independently. `applyPending(server, pending)` lays pending changes back on top of a server state.
  - Each todo is last-write-wins.
- **Client loop** — `src/hooks/useSync.ts`.
  - It's a no-op without an access code, so tests and code-less devices behave exactly as before.
  - With a code, it syncs on mount, on `visibilitychange` to visible, on `online`, and 800 ms after the last local change while anything is pending.
  - A sync pushes the pending diff, or just `GET`s when nothing is pending. It then sets `base = server` and `state = applyPending(server, diffState(sent, now))`. Only changes made while the request was out get re-applied, so an edit the server refused (tombstone) disappears instead of looping.
  - One request at a time; a trigger during a request queues one more round.
  - A device's first sync is this same loop with an empty base: all its local tasks upload and merge with the server's by id.
  - Exposes `status` (`local | pending | synced | offline | bad-key`) and `connect(code)`.
- `src/sync/api.ts` provides `fetchState`, `pushChanges`, and `SyncError` with `failure: 'bad-key' | 'offline'`. `src/sync/config.ts` provides `API_URL`, from `VITE_API_URL` in `.env.development` / `.env.production` (unset under Vitest, so tests call relative URLs), and handles the `#cle=` link.
- Tests: `src/sync/diff.test.ts` covers the pure model. `src/hooks/useSync.test.ts` runs the loop against an in-memory fake of the worker, with `fetch` stubbed via `vi.stubGlobal`.
